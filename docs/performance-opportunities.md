# ReLift Performance Investigation

Status: The individual screening experiments below have been measured. See the [experiment log](optimization-experiment-log.md) for results, failed numerical gates and keep/discard decisions. Combined full-pipeline confirmation is recorded separately from isolated stage measurements.

The [native optimization campaign](native-optimization-experiments/README.md) implements four optional C++/CUDA experiments with shared configuration and dependency injection. Its results include corrected CUDA arithmetic/validation bugs, repeated RAM measurements and a separate disk pilot. These measurements remain separate from the earlier experiments below.

The original plan below investigates streamed-path overhead, redundant setup, transfer overlap and model reuse. Offloading addresses capacity and can make a run slower. Each optimization is measured separately from the [offload comparison](offload-benchmark-analysis.md) so its effect is identifiable.

## What the new comparison changes

The five paired swing-tire trials establish a capacity/runtime tradeoff: RAM placement reduces sampled device memory while increasing wall time. The forced disk trial has approximately the same sampled GPU peak as RAM placement but spends much longer in DA3 and writes large cold archives. Those results support using RAM before forced disk on this machine; they do not establish a general speed advantage for offloading.

Host-memory comparisons use sampled process-tree RSS. Candidate stage records also contain process RSS high water, which catches peaks that the sampler can miss; that metric was not captured by the frozen baseline. Similar sampled RSS across methods therefore does not prove identical true RAM peaks. Disk mapping also uses resident file pages and the OS page cache.

The interactive exporter now reads selected tracks from mapped files, and trajectory shards are already written in seeded group order. Those two original proposals are implemented. What remains is to measure their exporter-only/preparation costs and optimize additional transfers, copies and validation scans. Neither should be presented as a future feature that has yet to be built.

The [comparison viewer](../outputs/benchmark-charts/index.html) and its CSV/JSON show the selected recorded trials, trial counts and ranges. Saved dense-output allocation is inventoried separately from timed physical disk I/O. Temporary scratch peak was not recorded; measuring that is part of the next profiling experiment.

## What the existing timings suggest

For swing-tire, the logged DA3 stage takes 23 seconds, while its logged model forward takes 9.94 seconds; AllTracker takes 5 seconds and correction takes 3.6 seconds. The approximately 13-second gap includes initialization, preprocessing and other wrapper work. It cannot all be attributed to weight loading without new instrumentation. Spin has a larger processed grid and takes 13.76 seconds in DA3 forward versus 9.94 for swing-tire, but these are different inputs and single runs, not a controlled resolution-scaling experiment.

DA3 is the largest logged stage in these examples. Optimizing the 3.6-second corrector alone cannot remove DA3's cost. Reducing a small stage to zero also gives an upper bound on the possible end-to-end improvement, which should guide where profiling effort goes.

Evidence is captured in [the observational inventory](../outputs/analysis/current-demo-performance.json), generated by [analyze_demo_performance.py](../scripts/analyze_demo_performance.py). The inventory records log precision and omitted work. No numerical speedup estimate is assigned to the candidates below.

## Confirmed code paths

The [AllTracker wrapper](../relift/providers/alltracker.py) now skips discarded pretrained initialization before strictly loading the released checkpoint. Controlled loaded-state and raw-output checks passed; see the experiment log. The original behavior is visible in the pinned upstream [Net constructor](https://github.com/aharley/alltracker/blob/c1ed462b7cfe9b4c6d07d8880ae5ed103b0848e0/nets/alltracker.py) and [ConvNeXt initialization](https://github.com/aharley/alltracker/blob/c1ed462b7cfe9b4c6d07d8880ae5ed103b0848e0/nets/blocks.py).

AllTracker's CNN feature extraction already processes clips longer than 64 frames in chunks. It then concatenates and retains the feature tensors, while [the wrapper](../relift/providers/alltracker.py) has already sent the complete float32 image sequence to the GPU. Adding another outer frame loop is not enough; inspect live feature lifetimes and reference-frame reuse. A sliding-window tracker path can change correspondence predictions and belongs in a separate quality experiment.

[Checkpoint loading](../relift/checkpoint.py) loads the corrector state onto the requested device before allocating and loading the model there. A CPU-backed or mapped load may reduce transient duplicate GPU state, but the corrector is much smaller than DA3, so this is a secondary memory cleanup rather than the main capacity fix.

The batch validates full trajectory hashes before reuse, and the exporter computes a hash after export. Those sequential scans improve integrity and may become a visible cost on larger arrays. Instrument them before considering a trusted immutable chunk manifest that avoids redundant scans. Never replace an integrity check with a filename or size check alone.

## Experiments that need a separate quality decision

Lower resolution, fewer tracker iterations, changed temporal windows, lower precision, weight quantization, and alternate checkpoints can improve capacity or speed, but they change the inference problem or numerical behavior. Report their accuracy and temporal-coverage effects separately from storage and placement optimizations.

Global DA3 attention makes temporal splitting especially significant. A shorter prefix is not equivalent to the corresponding frames of a longer joint inference run. Joining independently estimated windows also requires explicit camera and scale alignment and continuity checks.

Avoid adopting every familiar optimization by default. DA3 already uses inference mode and autocast, the corrector already disables gradients and uses bfloat16 autocast, and both use PyTorch attention operations. Replacing these paths requires evidence from a profile. Activation checkpointing aimed at backward graphs is not a general remedy for the tensors retained during inference.

## Original investigation order

First, collect a baseline profile with model construction, preprocessing, CUDA execution, copies, serialization, hashing and HTML generation separated. Profile one ordinary clip and one long failure in diagnostic runs; use unprofiled trials for timing comparisons because profiler settings can add overhead. [PyTorch profiler](https://docs.pytorch.org/docs/2.11/profiler.html)

Then test bounded depth reuse, redundant initialization and unnecessary copies individually. Reuse the same inputs, settings and cache policy and compare each patch against the implemented offload path as well as the frozen original. Follow with transfer overlap, batch tuning and model reuse. Compilation comes last because startup, specialization and memory costs can obscure simpler improvements.

Use repeated paired trials, not a single best run, and retain raw points and observed ranges. Separate fresh inference, prepared-window correction, viewer export and resume: a cache hit is not a faster inference run. Check CUDA numerical parity, full frame coverage, pixel identity and visibility masks before interpreting a faster time. Keep the documented padded-duplicate policy explicit. Measure scratch peak and final output/cache sizes separately from physical disk traffic, with warm and reproducibly cold caches treated as different experiments.

For each experiment, retain a short record: hypothesis, code change, workload and cache policy, correctness result, peak GPU/RAM/scratch use, physical I/O, individual timings, median change, and the decision to keep or discard it. Preserve unsuccessful experiments as evidence rather than combining all changes into an unexplained final speedup.

This update uses the saved offload trials and current implementation. Generating the comparison charts reads those records and inventories saved dense files; it does not rerun inference or apply any of the proposed speed-optimization patches.
