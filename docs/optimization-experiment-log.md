# Sequential optimization experiments

The reference is the runnable snapshot in `outputs/experiments/offload-reference`.
It contains the completed offload implementation before these optimization patches.
The earlier original implementation is separately preserved in `outputs/benchmarks/baseline-source`.

`configs/experiments/optimization.json` describes explicit source snapshots, workloads,
variants and trial counts. `scripts/run_optimization_experiments.py` executes them sequentially,
alternating paired order and retaining per-trial commands, code hashes, logs, sampled GPU/host
memory, I/O and output-directory allocation. Current output allocation is sampled separately
from physical writes; sampling can miss short-lived peaks. Completed-stage fixtures are copied
outside measured process time; inference is not relabeled as a full pipeline benchmark.

The generic measurement summary is generated by
`scripts/summarize_optimization_experiments.py outputs/experiments/optimization`.
Interpretation and keep/discard decisions belong in this document, not in that renderer.

## 1. Profile the existing offload path

Completed a diagnostic correction-only run over the same 84-frame, 280×504 prepared inputs,
group 1024 and batch 8. The source is the unmodified offload snapshot. The diagnostic captures
cProfile statistics, synchronized inclusive spans and a CUDA trace over two active batches.
Its runtime is not an unprofiled performance result and cannot be compared to previous timings.

Observed inclusive spans are approximately 3.70 seconds for correction, 3.15 seconds for shard
commits and 0.82 seconds for rays. Hash updates account for about 2.11 seconds of CPU self time
across multiple stages; fsync accounts for about 1.44 seconds. These categories overlap, so
their sum would be invalid. The profile suggests storage and hashing deserve attention as well
as repeated depth transfer. The unchanged durability and corruption-detection policy remain
constraints on experiments that reduce serialization overhead.

Evidence: `outputs/experiments/optimization/profile/diagnostic/trial-01/output/diagnostic.json`,
`cpu-profile.pstats`, `cuda-trace.json` and the trial telemetry.

## 2. Bound and reuse depth data

Compared the frozen reference against one persistent float32 depth tensor,
limited to 256 MiB and disabled when the clip or available CUDA memory cannot accommodate it.
Ray sampling still uses CUDA nearest-neighbor sampling over the original grid, in the same
16-frame blocks. Full trajectories and cameras remain unchanged inputs to the corrector.

Five alternating pairs completed. Median correction stage time increased from approximately
17.54 to 18.53 seconds; fresh-process median increased from 19.53 to 20.53 seconds. Sampled GPU
memory increased by about 48 MiB. The tested cache is not enabled by default because it did not
improve this workload. Its implementation remains an explicit experimental option and its source
snapshot is preserved for reproduction. The CPU test checks selected-ray identity and budget fallback;
the complete CUDA comparison is saved separately with the experiment.

## 3. Skip discarded AllTracker initialization

Completed five pairs comparing original construction with `init_weights=False`, followed by strict
loading of the same released checkpoint. Construction and forward execution are timed separately.
All loaded parameter/buffer hashes and raw float32 tracker outputs match across all ten runs.
Median constructor time fell from 1.406 to 1.066 seconds (about 24%); isolated provider-process
time fell from 8.515 to 8.146 seconds (about 4.3%). Forward time remained approximately 4.5 seconds.
Keep this change for final integration, subject to the end-to-end confirmation. It does not alter
the released weights or tracker iteration settings.

## 4a. Remove redundant provider array copies

Completed five pairs changing only AllTracker's already-float32 return conversion to
`astype(..., copy=False)`. Construction still uses the original pretrained initialization for
this isolated experiment. Raw tracker artifacts and loaded state match in all ten runs.
Median fresh-process time changed from 8.581 to 8.492 seconds (about 1%); the forward stage
changed from 4.506 to 4.489 seconds. This is a small measured effect, with negligible change
in sampled host memory. Retain it for integrated confirmation; no DA3 copy saving was measured.

## 4b. Hash NPY bytes while writing

Completed five pairs changing only shard hashing: the candidate hashes bytes accepted by the
writer rather than reopening each newly written NPY file for its initial checksum. Flush/fsync,
manifest commits, final verification and resume validation remain in place. Full trajectories,
including padded repeated pixels, pass the numerical gate.

Median correction time fell from 17.982 to 16.498 seconds (about 8.3%); fresh-process time fell
from 20.034 to 18.578 seconds (about 7.3%). GPU memory, host memory and physical writes were
approximately unchanged. Retain this change for integrated confirmation.

## Runtime migration

The completed screening measurements above used Python 3.10.22. The project now targets Python
3.13. Subsequent experiments must record the actual interpreter and installed package versions,
and each comparison must run both variants in that same environment. Existing measurements
are historical evidence; they are not silently relabeled or pooled with Python 3.13 trials.
